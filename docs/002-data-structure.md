# Jot Deck データ構造

## 1. データモデル

### 1.1 エンティティ関係

```
Deck (1) ─────< Column (n) ─────< Card (n)
                                    │
                                    └───< Tag (n:n)
```

### 1.2 各エンティティの属性

#### Deck
| 属性 | 説明 |
|:---|:---|
| **name** | Deck 名 |
| **sort_order** | カードのソート順設定（`created_desc` / `created_asc` / `score_desc` / `score_asc`、デフォルト `created_desc`）。表示順への反映は未実装で、カードは `position` 順に表示する |

#### Column
| 属性 | 説明 |
|:---|:---|
| **name** | Column 名（表示用） |
| **position** | 表示順序。Deck 内の生存カラムで 0 始まりの欠番なし連番を保つ（GUI は表示 index をそのまま position として送るため）。挿入・移動・復元先が負なら先頭、末尾を越えれば末尾に丸め、DB 初期化時に欠番を詰め直す。Card の position も Column 内で同じ規則 |
| **description** | このカラムに何を入れるかの 1 行説明（分類軸）。外部エージェントの振り分け精度に効く（`008-mcp-server.md` §4.6） |
| **private** | 非公開フラグ。true のカラムは外部の書き込み口・MCP から一切読み書きできない（`008-mcp-server.md` §4.5） |

#### Card
| 属性 | 説明 |
|:---|:---|
| **content** | テキスト内容 |
| **score** | 重要度（favorite 数） |
| **updated_at** | カードへの書き込み（作成・content 編集・score 変更・移動・論理削除など）のたびに進む UTC タイムスタンプ（RFC3339 文字列で保持）。楽観ロック（compare-and-swap）の条件値であり、読んだ時点の値と一致するときだけ確定更新を適用する（→ §5.3） |
| **locked_by** | 現在この Card を占有している編集主体。`null`＝未占有／GUI 編集セッションごとに生成する一意の所有者 ID＝手編集中／書き込み元識別子（AI 書き込み接続の ID 等）＝AI 編集中（→ §5） |
| **locked_at** | 占有ロックの取得時刻。ここから一定時間（リース）で失効する（→ §5.2） |

#### Tag
| 属性 | 説明 |
|:---|:---|
| **name** | タグ名（`#` を除く） |

## 2. タグ抽出ルール

* パターン: `#` + 英数字・アンダースコア・日本語（ひらがな・カタカナ・漢字）
* 例: `#todo`, `#2024`, `#アイデア`, `#重要_メモ`

## 3. 論理削除と物理削除

### 3.1 削除フロー

1. **論理削除:** ユーザーが削除操作を行うと、データは非表示になるが保持される。
2. **復元:** ゴミ箱から復元可能。
3. **物理削除:** 論理削除から 30 日後に自動で完全削除（アプリ起動時に実行）。

例外として、新規作成直後に空のまま編集を終えた Card は、論理削除を経由せずその場で物理削除する（ゴミ箱にも Undo 履歴にも残らない。`docs/001-keybindings.md` §5 参照）。削除は有効なリースを持つ編集ロックの所有者が、内容が空白のみの Card に対してだけ行える。

### 3.2 Column 削除時の連動

* Column を削除すると、所属する Card も連動して論理削除される。
* Column を復元すると、連動削除された Card も復元される。
* Card 単体で削除された場合は Column 復元の影響を受けない。

### 3.3 削除スタック（ゴミ箱）

* 論理削除された Column / Card は `deleted_at` 付きで SQLite に残り、ゴミ箱 UI（`g t`）に削除日時の新しい順で並ぶ（Column と連動削除された Card は Column の項目にまとめ、個別には並べない）。
* ゴミ箱 UI からは任意の項目を選択して復元可能。
* `u`（Undo）はセッション内の操作履歴に対する汎用 Undo であり、履歴に残っている削除はこれでも取り消せる（`001-keybindings.md` §4.4）。
* 論理削除から 30 日経過で自動的に物理削除。

## 4. セッション状態の永続化

以下の状態はフォーカスが変わるたびに Deck ごとに保存され、次にその Deck を開いたとき（次回起動時を含む）に復元される。

| 状態 | 説明 |
|:---|:---|
| **フォーカス位置** | 最後にフォーカスされた Column インデックス |
| **カラム別カードフォーカス** | 各 Column で最後にフォーカスされた Card インデックス |
| **フォーカスモード** | Column / Card のどちらか（Edit / Command は復元しない）。Card はフォーカス先の Column にカードがあるときだけ復元する |

* 保存先: WebView の localStorage（Deck ID ごとのキー）。Deck を削除するとその Deck の保存状態も消す
* 最後に開いていた Deck の ID も localStorage に保存し、起動時に自動で開く
* ゴミ箱は SQLite（`deleted_at`）に、Undo / Redo の操作履歴はセッション中のメモリ上のみに保持されるため、ここには含まない

## 5. カード編集の競合制御

1 枚の Card を、人間の手編集と AI 書き込み（MCP / Reporter 経由）が同時に触ると、内容が壊れる・更新が失われる。これを **①占有ロック（編集中の排他）** と **②楽観ロック（確定書き込みの取り違え防止）** の二段で防ぐ。ロックは Card 単位であり、Card を跨がない編集は互いに干渉しない。

### 5.1 原則

* **1 枚の Card は同時に一人だけが占有できる。** 占有者は「手編集中のユーザ」か「ストリーム書き込み中の Reporter」のいずれか。
* 占有中、他方からの占有（手編集の開始・ストリーム開始）は**拒否**され、AI 占有中のカードは UI 上 read-only（`◍ AI generating` 表示）として見える。
* 占有ロックを取らない確定書き込み（MCP の `patch_card`）は占有を見ず、楽観ロック（§5.3）だけで守る。手編集中のカードに `patch_card` が適用された場合、手編集側の次の保存が楽観ロックで拒否される。
* position の採番と同じく、ロックの取得・解放・失効判定は Card Repository に一元化する（編集主体に委ねない）。

### 5.2 占有ロック（排他）

`locked_by` / `locked_at`（→ §1.2）で Card の占有を表す。

* **取得**: 編集開始時に `locked_by` を自分に立てる。
  * 手編集: edit フォーカス進入時（エディタを開くとき）。
  * AI 編集: Reporter のストリーム開始時（`card.stream.begin`）。
  * 既に他者が占有していれば取得失敗 → 編集を開始できない。
* **解放**: 編集終了時に `locked_by` を `null` に戻す（手編集は `:wq` / `Ctrl+Enter` での保存終了または破棄終了、Reporter は `card.stream.end` の確定と同時）。edit フォーカスを外してもエディタは開いたままなのでロックは保持される。
* **リース失効**: `locked_at` から一定時間（120 秒）を過ぎたロックは自動失効し、他者が奪取できる。編集の放棄や書き込み側のクラッシュで Card が永久ロックになるのを防ぐ。リース上限は「開いたままにできる最大時間」の backstop と同根。手編集中は GUI が定期的にロックを取り直してリースを延長する。

### 5.3 楽観ロック（ロスト更新の防止）

占有ロックを取らない短い確定編集どうしが競うと、後勝ちで更新が失われる。**確定更新（content の書き換え）は `updated_at` を条件とする compare-and-swap** で守る。

* 呼び出し側は、読んだ時点の `updated_at` を確定更新に添える。
* Repository は現在値と一致するときだけ更新を適用し、`updated_at` を進める。不一致（間に他者が更新済み）なら**拒否** → 呼び出し側は再読込して内容を確認し、必要なら再試行する。
